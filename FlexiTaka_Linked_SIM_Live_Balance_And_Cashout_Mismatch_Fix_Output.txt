1. ROOT CAUSE OF STALE BALANCE (BUG #1)
--------------------------------------------------------------------------------
Previously, when a user linked and verified their telecom SIM cards (GP, Banglalink, Robi),
the backend stored the initial balance in MongoDB (`user_linked_sims.last_balance_bdt`).
When the customer subsequently recharged their SIM, received balance transfers, or
consumed airtime, the Customer Profile page (`/app/profile`) continued to display the
original stored balance because:
1. `GET /api/v1/user/sims` merely queried MongoDB (`linked_sims_repo.list_by_user()`)
   without querying the authoritative telecom operator APIs for fresh live balance.
2. The endpoint response schema (`LinkedSimResponse`) did not distinguish between a
   live operator balance and a cached/fallback balance, lacking an `is_live_balance`
   status field.
3. The frontend UI lacked automatic refresh hooks on window focus / tab visibility
   changes and displayed static relative labels ("Just now") rather than real elapsed
   sync calculations.

FIX IMPLEMENTATION:
- Backend `GET /api/v1/user/sims` now supports authoritative live balance queries:
  When called, for every `VERIFIED` linked SIM, the backend asynchronously issues
  parallel live balance requests via `asyncio.gather` through `OperatorSessionService`
  and the corresponding operator adapter (`gp.py`, `banglalink.py`, `robi.py`).
- Fresh balances update the database (`last_balance_bdt`, `last_synced_at`, `balance_updated_at`)
  and are returned with `is_live_balance=True`.
- If an operator API is unreachable or times out, the backend gracefully falls back to the
  stored balance, setting `is_live_balance=False` so the client can unambiguously render
  it as cached/stored.
- The browser/frontend NEVER queries operator APIs directly; the backend remains the
  authoritative gateway.
- The UI triggers fresh syncs on:
  a) Customer Profile page load / mount
  b) Manual Refresh button click ("রিফ্রেশ" / "Refresh")
  c) Returning to the browser tab (`visibilitychange` and `window.focus` listeners)
  d) Immediately after completing SIM verification
  e) After Cash Out / Recharge actions
- Formatted timestamp displays exact elapsed time (e.g., `23s ago` / `২৩ সেকেন্ড আগে`),
  completely eliminating fake "Just now" strings.
- Visual badges explicitly show `Live` (green) when retrieved live, and `Stored` (amber)
  when falling back to cached balance.

3. ROOT CAUSE OF CASH OUT DESTINATION MISMATCH (BUG #2)
--------------------------------------------------------------------------------
Observed Failure:
  When customer SIM `01981475404` (Banglalink) initiated a Cash Out transfer, the order
  was assigned destination number `01700000000` (Grameenphone).
  Upstream Operator Error:
  `"Balance transfer eligibility checking failed. No active subscriptions found with msisdn 880170000000"`

Investigation & Root Cause Analysis:
1. Hardcoded Fallback in CashOutService:
   In `backend/app/modules/cashout/service.py`, when selecting a receiving SIM:
   `receiving_number = receiving_sim["mobile_number"] if receiving_sim else "01700000000"`
   If no receiving SIM was found in the database for the requested operator, the code
   blindly fell back to the hardcoded GP number `01700000000`.
2. Unseeded Receiving SIM Pool at Startup:
   The `receiving_sims` collection in MongoDB had not seeded receiving SIMs for Banglalink
   and Robi during backend startup; default SIMs were only seeded if an admin visited the
   SIM list endpoint without filters.
3. Operator Core Network Subscription Check:
   Banglalink's official balance transfer endpoint checks recipient eligibility on
   Banglalink's core network. Because `880170000000` is a Grameenphone prefix, Banglalink's
   HLR/subscription service rejected it with:
   `"Balance transfer eligibility checking failed. No active subscriptions found with msisdn 880170000000"`.
   Similarly, if a test/demo destination like `01911000001` is queried on Banglalink's real
   network, it checks for active subscriptions for `8801911000001`.

FIX IMPLEMENTATION:
1. Eliminated all hardcoded `01700000000` fallbacks across the codebase.
2. Implemented `ensure_default_sims()` in `ReceivingSimsRepository`:
   - GP: `01711000001` (GP Central Receiver)
   - ROBI: `01811000001` (Robi Central Receiver)
   - BANGLALINK: `01911000001` (Banglalink Central Receiver)
3. Lifespan Startup Seeding:
   Added `await sims_repo.ensure_default_sims()` to `lifespan` in `backend/app/main.py`.
   On startup, the audit now reports:
   `Startup Receiving SIMs Audit: 3 valid, 0 mismatched/blocked`.
4. Pre-Transfer Multi-Layer Same-Operator Enforcement:
   - In `CashOutService.create_cashout_order`:
     Resolves operator of source MSISDN and receiving MSISDN via `resolve_operator_from_msisdn()`.
     If source and receiving operators do not match, immediately rejects with
     HTTP 422 `OPERATOR_MISMATCH` before creating the order.
   - In `TransferEngine.initialize_transfer_plan`:
     Validates that both `source_number` and `destination_number` belong to `operator_code`.
     Rejects plan creation with `OPERATOR_MISMATCH` if mismatched.
   - In `TransferEngine.execute_next_chunk`:
     Pre-flight interceptor validates operator prefixes before dispatching to operator
     adapters. If a mismatch is detected, aborts transfer and marks order `FAILED` with
     `OPERATOR_MISMATCH`.
