6. API CHANGES & ENDPOINT SPECIFICATION
================================================================================
1. `GET /api/v1/user/profile`
   - Headers: `Authorization: Bearer <token>`
   - Response: `UserProfileResponse` (user_id, phone, name, email, language_preference, status, created_at, linked_sims_count)
2. `PUT /api/v1/user/profile`
   - Headers: `Authorization: Bearer <token>`
   - Body: `{"name": "...", "email": "...", "language_preference": "bn"|"en"}`
   - Response: Updated `UserProfileResponse`
3. `GET /api/v1/user/sims`
   - Headers: `Authorization: Bearer <token>`
   - Response: `List[LinkedSimResponse]`
4. `POST /api/v1/user/sims`
   - Headers: `Authorization: Bearer <token>`
   - Body: `{"phone": "017XXXXXXXX", "label": "Personal GP"}`
   - Validation: BD phone format, operator detection from prefix registry, duplicate SIM check.
   - Response: Created `LinkedSimResponse` (status: "UNVERIFIED")
5. `POST /api/v1/user/sims/{sim_id}/request-otp`
   - Headers: `Authorization: Bearer <token>`
   - Initiates Operator OTP challenge to the customer's SIM via operator gateway.
   - Response: `{"success": true, "reference_id": "...", "operator_code": "GP", "message": "..."}`
6. `POST /api/v1/user/sims/{sim_id}/verify-otp`
   - Headers: `Authorization: Bearer <token>`
   - Body: `{"otp": "1234", "reference_id": "..."}`
   - Validates OTP with operator gateway, stores ephemeral encrypted session token,
     updates SIM status to `VERIFIED` and records `verified_at` timestamp.
   - Response: Updated `LinkedSimResponse`
7. `DELETE /api/v1/user/sims/{sim_id}`
   - Headers: `Authorization: Bearer <token>`
   - Validates ownership (no IDOR) and removes linked SIM from account.
   - Response: `{"success": true, "message": "Linked SIM removed successfully"}`
8. `POST /api/v1/auth/logout`
   - Headers: `Authorization: Bearer <token>`
   - Extracts JWT `jti` and expires it in Redis for the remainder of its lifetime (up to 7 days).
   - Response: `{"success": true, "message": "Successfully logged out"}`

8. AUTHENTICATION FLOW
================================================================================
1. Customer enters mobile phone (e.g., 017XXXXXXXX).
2. Backend generates a 6-digit cryptographic OTP, sends via ZendSMS, and stores
   the hash in Redis with a 5-minute TTL. Rate limiting: 3 OTP requests / 15 mins.
3. Customer submits OTP.
4. Backend verifies hash, marks phone verified, generates standard HS256 JWT,
   and links any prior guest orders from `guest_session_id` to `user.user_id`.
5. On logout, `POST /auth/logout` blacklists the JWT in Redis. Future API requests
   with this JWT immediately receive 401 Unauthorized.
6. Operator OTP is strictly NOT used for FlexiTaka account login.

================================================================================
9. LINKED SIM FLOW
================================================================================
1. Logged-in customer submits phone number to add under their account.
2. Backend verifies operator prefix from authoritative prefix registry.
3. Backend checks uniqueness: prevents duplicate registration of the same phone number
   under the same account and across active linked SIMs.
4. SIM is created in `UNVERIFIED` state.
5. Customer clicks "Verify Operator OTP".
6. Operator challenge is requested via telecom gateway (`request-otp`).
7. Customer enters operator OTP.
8. Operator session is established securely on backend. SIM is marked `VERIFIED`.
9. PINs, passwords, and raw operator tokens are NEVER stored in the database or sent to frontend.

================================================================================
10. SECURITY IMPLEMENTATIONS
================================================================================
- Strict OTP Separation:
  * FlexiTaka Account OTP: Account authentication only.
  * Operator OTP: Telecom SIM verification only.
  * Recharge: Zero OTP required.
- Non-Custodial: No SIM PINs, passwords, or raw telecom tokens stored or transmitted.
- IDOR Protection: All profile and SIM mutations verify `sim.user_id == current_user.user_id`.
- Replay & Revocation: Blacklisted tokens stored in Redis with TTL matching JWT expiration.
- Rate Limiting: OTP request throttled to prevent SMS flooding.
